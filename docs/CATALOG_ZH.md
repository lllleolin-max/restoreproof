# RestoreProof 中文目录说明

**做什么**：为停止写入的小型 SQLite+资源文件应用执行真实恢复演练。它生成文件快照，恢复到新建目录，在恢复出的数据库上检查完整性、外键、声明的消费者查询和资源引用，输出分层 JSON 结论。恢复失败的目录被明确标为部分失败或应用失败，不能当成成功恢复。

**怎么用**：先按 README 构建并普通安装 wheel；运行 `python tools/verify_workflow.py` 验证真实 CLI 和独立资源检查。随后使用 `restoreproof fixture pilot/app` 创建合成示例，`snapshot --source ... --spec ... --out ...` 创建快照，`drill --archive ... --manifest ... --parent ...` 演练恢复。自己的应用需要提供消费者查询的精确预期值和完整的资源引用查询；数据库必须停止写入且无 WAL/journal/shm。

**为什么做**：单个文件的哈希正确不代表恢复后的应用引用关系正确。七场景对照中，同一份全哈希正确归档仍可因数据库指向不存在或摘要不符的附件而失败。该机制能把附件检查纳入重复演练，减少分散的手动核验；经济收益是试点假设，需要用户实际测量。

| 评价轴 | 已实现的可核验证据 | 局限与未知 |
|---|---|---|
| 商业价值 | 明确的小型 SQLite 应用维护者工作流；普通 wheel/CLI；完整输入到 JSON 结论；具体人工检查节省假设 | 没有客户、收入、付费意愿或实际人工成本测量；只适合明确的小应用范围 |
| 技术价值 | 严格 ZIP32 实际字节解压计数；原始路径与碰撞检查；只读 SQLite 授权器和 VM/时间/结果预算；43 项当前测试；真实源数据/目标查询独立预言机；三轮历史 wheel 原样探针验证 | 本地执行为 Windows/Python 3.14.3；Linux/3.11 需实际 CI；可信本地主机假设、合作式时间预算，无 OS 沙箱 |
| 创新价值 | 在相同真实归档上关闭应用检查作公平基线；数据库/附件不一致真实改变决策；字节、快照、应用检查分层，失败状态可诊断 | 复用 ZIP、SHA 与 SQLite 已有机制；未运行 restic，不能推断其缺少类似集成或宣称优于它；断言覆盖范围由维护者声明 |

这里不提供建造者自评分。三个轴的最终分数和是否严格超过 80，应由固定量表下的独立评审在精确提交上决定。演练耗时不是 RTO/RPO 或灾难恢复就绪证明，摘要也不是来源身份认证。
