# Architecture and costs

`snapshot` walks regular single-link source files, validates portable names, records initial hashes, copies in chunks to deterministic ZIP32 entries, rechecks inventory/hashes and SQLite's standalone header/sidecars, then writes a manifest. Output is always a new directory. A failed build retains `FAILED` and incomplete artifacts. Source writes must be stopped externally; repeated hashes cannot establish atomicity or detect a write-and-revert race.

`plan` parses only capped metadata. The custom ZIP32 reader exists because an ordinary ZIP reader can truncate output to an advertised size: RestoreProof instead directly decompresses the full declared compressed extent and counts actual bytes. It rejects hidden/overlapping extents, disagreed headers and unsupported extension metadata. Parsing O(m + archive-name-bytes); path validation O(total component spelling bytes). Manifest and inventory are memory-bounded by input/member caps.

`drill` fingerprints the source inputs, preflights metadata and naming, allocates a new `tempfile.mkdtemp` child of the trusted parent, streams each file to exclusive creation, and checks actual size/CRC/SHA. Failure is explicit; failed directories are not auto-deleted. Restore I/O and hashing O(compressed + decompressed bytes), transient decompression buffers ≤64 KiB, inventory O(m). Archive input hashes are rechecked after the operation. Existing parent contents are untouched.

After complete byte restoration, one URI `mode=ro&immutable=1` SQLite connection checks schema, integrity, foreign keys, exact typed consumer results and asset reference queries. No ATTACH, changes, extension loading or shell commands. SQLite authorizer actions allow SELECT/READ/recursive CTE and a small built-in function list. Internal integrity/foreign-key pragmas are specifically authorized; user pragmas are denied. Connection length/SQL/column/expression/compound/attachment limits, progress callback and shared row/result counters bound the declared subset. The timer is cooperative, not a hard OS deadline: parsing/native work can occur between callback opportunities. File-size and SQLite length limits provide additional bounds; this is not a hostile native-code sandbox.

Application work runs on the actual restored database. Asset digests are those measured on actual extracted bytes, under the trusted host/no concurrent destination mutation assumption. A successful asset assertion can therefore disagree with and override a hash-only acceptance decision even when every archive file matches its manifest. A malicious manifest can reframe expectations; no origin verification is promised.

SQLite query complexity is workload-dependent. VM/result budgets deliberately return failure rather than a completion guarantee. Large/unsupported legitimate applications can fail within the useful small-app scope. An exhausted check does not establish application inconsistency; the issue is `QUERY_BUDGET`, distinct from `ASSET_MISMATCH` or `QUERY_EXPECTATION`.
