# Strict formats, version 1

All JSON is bounded UTF-8. Duplicate object keys, nonfinite numbers, unknown keys and boolean-as-integer values are rejected. Example `application.json` is generated by `restoreproof fixture` and deliberately lives outside the source tree:

```json
{
  "format": "restoreproof-app-v1",
  "database": "library.sqlite",
  "queries": [{"id": "document_count", "sql": "SELECT count(*) FROM documents", "expected": [[{"type":"integer","value":2}]]}],
  "assets": [{"id": "document_assets", "sql": "SELECT path,sha256 FROM documents ORDER BY id"}]
}
```

At least one query and asset query are required; total count defaults to 32. Identifiers are unique ASCII `[A-Za-z][A-Za-z0-9_-]{0,63}`. Consumer rows are compared exactly in order, column count, type and value. Use `ORDER BY` when order matters. Values are `{type,value}` pairs: `null`/JSON null, `integer`/signed 64-bit JSON integer, `text`/string, `blob`/lowercase even-length hex, or `real`/finite canonical Python `float.hex()` string. Integer 1 and real 1.0 are distinct; booleans are invalid integer expectations. Blob bytes and REAL bit representation survive JSON conversion. SQLite negative zero behavior follows the actual SQLite return value, not source SQL spelling.

Asset queries return exactly `(portable_path TEXT, lowercase_sha256 TEXT)`. Every returned reference must be a listed non-database file and match the actual restored bytes. Queries must cover the reference universe the operator wants checked; an empty or incomplete query does not prove that all possible application references are sound. The application descriptor is a trusted choice of assertions, not proof they capture every consumer behavior.

The snapshot manifest has exact keys `format`, `application`, `files`; format is `restoreproof-snapshot-v1`. `files` is an array of exact `{path,size,sha256}` objects. Paths are validated from their original spelling. Sizes are nonnegative actual byte counts, SHA-256 is lowercase hex. Array entries may be in any order but must be unique. Every archive file must appear exactly once, no missing or extra entries. The database must be listed.

Archive: single-disk ZIP32; each central/local header agrees, central directory covers exactly all contiguous local entries and ends directly before the 22-byte EOCD. Supported methods are stored (0) and raw deflate (8); flags only 0 or UTF-8 (0x800); names unflagged ASCII or flagged UTF-8. No encryption, data descriptors, comments, extra fields, prepended data, ZIP64 or multidisk files. UNIX/DOS regular entries only. Symlink/device/FIFO/directory/volume entries are rejected. ZIP has no portable hardlink entry in this subset; arbitrary extra fields that might encode such extensions are rejected. No metadata/permission restoration.

Portable names: relative NFC UTF-8, ≤240 bytes total; `/` separator, no empty/`.`/`..` component, `\\`, `:`, `< > " | ? *`, Unicode category C characters or trailing dot/space. Reject `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` and Windows superscript variants even with an extension. Casefold equivalence includes implicit directories: `Assets/a` and `assets/b` conflict. Files cannot prefix another file. This conservative policy can reject names a particular host permits. Host filesystem limits on the absolute destination can still cause an explicit I/O failure.

Default `Limits`: compressed archive 64 MiB, manifest 1 MiB, 2048 files, 16 MiB per file, 64 MiB actual total decompressed; 32 declared queries, 16 KiB SQL, 1,000,000 shared VM callback instructions, 4096 shared returned rows, 1 MiB shared encoded typed results, 256 KiB SQLite length/cell limit, 5 cooperative seconds for all application work. CLI `plan`/`drill` expose each bound as a hyphenated argument. Decompression yields at most 64 KiB chunks; one chunk can be decoded then rejected before writing, so peak transient decompressed memory is bounded but the reported attempted count can exceed the byte cap by ≤64 KiB. Metadata sizes never substitute for actual counters.

Report: `restoreproof-report-v1`, `decision` (`USABLE`, `BYTE_VERIFIED`, `FAILED`), separate `metadata_plan`, `byte_integrity`, `snapshot_agreement`, `application_assertions` (`passed`, `failed`, `not_run`), destination/lifecycle, issues, source fingerprints, limits, metrics and successful assertions. Snapshot agreement covers a completed file set and declared/actual size agreement; byte integrity covers CRC and manifest SHA-256. Preflight can pass `metadata_plan` while actual `snapshot_agreement` remains `not_run`. A failed partial extraction never certifies agreement: it remains `not_run` unless a concrete size/inventory discrepancy made it `failed`. SQL/asset failure preserves passed byte/inventory results. A FAILED decision must never be consumed as restore success. Paths in local reports may contain user filesystem names; sanitize them before sharing.
