# Security and reporting

Use a trusted local host, a real existing destination parent and operator-controlled stopped source. New destination isolation does not sandbox a hostile operating system, another process mutating paths or SQLite native vulnerabilities. Do not run as administrator to overcome an input failure. Links/devices/unsupported archive metadata are rejected; file creation is exclusive and original member spelling is validated conservatively.

SQL assertions have an authorizer allowlist and SQLite/VM/time/result budgets. No arbitrary shell commands or executable assertions exist. Budgets are cooperative, not a process sandbox or hard wall-clock kill. Snapshot digests and manifest agreement establish local byte evidence only; they do not authenticate an origin, identify a signer or prove the assertions cover the full application.

Reports and raw logs can include absolute destination paths. Keep raw files local and sanitize before publishing. No real customer/private fixtures are included. For a reproducible issue, use a synthetic archive/manifest and the installed version, issue code, platform and minimal commands. Report suspected vulnerabilities privately through repository security reporting when available; no guaranteed response SLA is offered.

Partial/failed directories are retained. Inspect the report before using contents; manually remove only the specifically reported throwaway child directory after review. Never treat `BYTE_VERIFIED` or `PLANNED` as application usability.
